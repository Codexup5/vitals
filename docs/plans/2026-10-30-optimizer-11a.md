## Decisions and trade-offs

- **Ids are stable slugs** (`games.hags`), not numbers — the decisions page says "numbers"; a slug says what it is in a
  recipe and in the journal and is validated against the catalog the same way. Renaming one needs an alias, which a
  test pins.
- **One Windows layer of the optimizer's own**, `optimize/windows.rs`, like the four domains that already have their
  registry wrapper (startup, services, updates, sensors) — a shared `registry` module would be DRY but means moving
  code four domains use: a refactor of its own, not part of a feature (KISS).
- **The apply order goes through a trait** (`optimize/apply.rs` over `trait Machine`): journal → one UAC (restore point,
  then HKLM) → HKCU. The order and "No changes nothing" are domain tests without Windows; `windows.rs` implements the
  trait. A declined prompt stops before any HKCU write, so "No" means nothing changed, as the decisions page promises.
- **A run without an admin item has no restore point**: making one needs admin rights, and asking for them only for the
  point would break "one UAC, only when needed". The journal is the way back for such a run; the preview says so.
- **The 24-hour limit is reported, not predicted**: reading restore points needs admin rights, so the elevated side
  compares the list before and after and reports "created" or "Windows kept the point of <time>". The preview says
  Windows makes at most one point a day. Turning System Protection on is an opt-in line of the same UAC when it is off.
- **A revert value comes from the user's journal**, so the elevated side writes it only to the key, the value name and
  the type the catalog declares for that id: the journal cannot steer it anywhere else.
- **Settings values, not policies, where Windows has both** (diagnostic data through the Settings path, not
  `SOFTWARE\Policies`), so Settings does not say "managed by your organization". Two items have only a policy (web
  search in Start, activity history); step 3 checks each against Microsoft's documentation and drops one without a
  documented value.
- **Out of 11a, from the decisions page's examples:** code folders out of the search index (a COM crawl-scope API with
  its own revert) and Windows Sandbox (an optional feature through DISM): both need their own kind of change and
  revert; they are candidates for 11d.
- **README changes land with the behaviour they describe:** the Safety lines of 11a in its last step, the Microsoft
  Store source with 11b, the machine-scope installs (and their `docs/deviations.md` line) with 11c. The rules the code
  follows (brief §7, `rust.md` §3) land first, in step 1. This is the approved edit, split by when each part becomes
  true.

**Out of scope:** apps and OneDrive (11b), programs (11c), the recipe file, the first-screen card, `--selftest-recipe`
and the sandbox (11d), the search index and Windows Sandbox items, the MCP server (reads only, no optimizer tool),
macOS.

## Risks and questions

- Settled in step 3: `games.dnd-fullscreen` left 11a — Windows 11 keeps the "do not disturb" rules in binary
  CloudStore blobs with no documented value; `base.start-web-search` is the documented policy
  `DisableSearchBoxSuggestions`, an admin item in HKLM, since a user may only read `HKCU\Software\Policies`;
  `base.activity-history` is the documented policy `PublishUserActivities`.
- `D3DKMTQueryAdapterInfo` lives in the WDK part of the `windows` crate (`Wdk_Graphics_Direct3D`); if the feature does
  not build, HAGS support falls back to "the value `HwSchMode` exists", which Windows writes only on a capable GPU — step
  10 says which one shipped.
- `Start_TrackDocs` = 0 also hides recent files in File Explorer and in jump lists; the row's description says so.
- Step 15 needs your UAC click once for the HKLM run and once for its revert; I give the moment, you press "Yes".
